3. AUTHENTICATION DESIGN OPTIONS
Preferred initial direction: a documented identity and session strategy chosen for the actual deployment environment.
If deployed as a browser-based application, evaluate secure server-managed sessions with HttpOnly, Secure, and appropriate SameSite cookies, plus CSRF protection for state-changing requests.
If deployed as an API for multiple clients, evaluate a supported identity provider or a carefully implemented token-based design with expiry, issuer/audience validation, and secure key management.
Do not store plaintext passwords, tokens, signing keys, or credentials in source code.
Use a maintained password-hashing implementation such as Argon2id if local password storage is selected; do not implement password hashing manually.
Do not add authentication dependencies until the deployment model and identity source are confirmed.

4. REQUIRED AUTHORIZATION BEHAVIOR
- Authentication must be enforced server-side, not only by hiding frontend controls.
- Every protected route must reject missing or invalid credentials.
- Valid users with insufficient permissions must be denied.
- Case updates must continue validating allowed status/severity values.
- Record the authenticated actor identity in audit events; do not trust a client-supplied actor ID.
- Do not permit unauthenticated user registration or privilege escalation.
- Keep health endpoint output minimal and avoid exposing secrets or environment details.

5. SECURITY TEST PLAN
- Unauthenticated request to protected case-list endpoint is rejected.
- Unauthenticated PATCH request is rejected and does not mutate a case.
- Viewer PATCH request is rejected and does not mutate a case.
- Analyst PATCH request succeeds for an authorized synthetic case.
- Administrator can access explicitly approved administrative actions.
- Invalid, expired, or malformed credentials are rejected.
- Audit actor identity comes from the authenticated principal.
- CSRF defenses are tested if cookie-based authentication is chosen.
- Existing health behavior and frontend build remain compatible.
- All tests use temporary SQLite databases and synthetic records.
